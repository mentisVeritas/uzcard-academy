## Условие

Владелец кредитного продукта: «Просрочка выросла. Нужна модель надёжности клиента». Обучать модель не нужно — вся работа до неё.

Главное — **таргет**. Готовой колонки `bad` в базе нет. По платежам решите, какое событие считать плохим и сколько месяцев наблюдать за договором. Защитите решение: почему такое событие и горизонт, что делать с договорами, не дожившими до конца окна, и с отклонёнными заявками.

**Данные:** Postgres `academy_db`, схема `public`, таблицы `scoring_*`. В выгрузке есть рабочие таблицы, старые копии, бэкапы и мусор. Если таблица выглядит подозрительно удобной — была бы эта информация у банка в момент решения?

**Порядок:** разведка всех `scoring_`-таблиц (ключи, периоды, когда появляется колонка) → таргет и bad rate по месяцам выдачи → фичи только до даты решения (анкета, бюро на дату решения, поведение по картам) → схема проверки (разбиение по времени, метрики, цена двух ошибок в деньгах).

<details><summary><b>Q6.</b> Таргет</summary>

Bad — хотя бы раз просрочка 90+ дней в первые 12 месяцев после выдачи. Источник — `scoring_contracts` + `scoring_payments`: DPD по `due_date` / `paid_date`, неоплаченные на 2025-05-31 тоже учитываются.

Отклонённые заявки (6 723) исключены — нет договора и платежей. Если 12 месяцев не прошло и 90+ нет — `target = NULL`; если 90+ уже есть — сразу bad.

На 5 874 зрелых договорах bad rate 11,2 % (656 bad). По полным 12-мес. когортам сильного роста нет (7–14 %). По 90+ за 6 мес. на свежих выдачах — рост с июня 2024: 16 % → 25 % (октябрь), это объясняет жалобу бизнеса.
</details>
