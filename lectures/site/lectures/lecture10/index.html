Вопрос аудитории

Как защитить данные от перехвата?

Только что вы видели: при обычном HTTP пароль и заголовки лежат в пакете чистым текстом. Любой, кто слушает Wi-Fi, прочитает их.

Что нужно добавить, чтобы человек посередине видел только зашифрованный поток?

Ответ

HTTPS: тот же HTTP поверх TLS

TLS оборачивает HTTP в шифрованный канал. Стартовая строка, заголовки и тело передаются в зашифрованном виде. Перехватчик в Wi-Fi видит только бессмысленные байты, домен (через SNI) и IP-адрес сервера.

Современный браузер показывает замок в адресной строке, когда соединение по HTTPS. На обычный HTTP браузеры ставят пометку «Not Secure» и всё чаще вовсе блокируют отправку форм с паролем.

Дальше в лекции разберём, что именно делает TLS и почему HTTPS закрывает почти все каналы утечки на пути от клиента до сервера.

DNS

Телефонная книга интернета

Серверы знают только IP-адреса вида 142.250.184.78. Люди удобнее запоминают google.com. DNS (Domain Name System) переводит имя в IP-адрес.

DNS
IP для машин
142.250.184.78
по нему маршрутизаторы доставляют пакеты

До любого HTTP-запроса браузер делает DNS-запрос. Без перевода имени в IP пакет некуда отправлять.

DNS

Как происходит DNS-запрос

DNS работает иерархически. Если ответа нет в кеше, запрос проходит через несколько уровней серверов, начиная от корневого.

1
Кеш браузера. Был ли уже такой запрос за последние минуты? Если да, IP берётся оттуда.
2
DNS-резолвер провайдера. Системный запрос идёт к нему. У него тоже есть кеш.
3
Корневой сервер. Резолвер спрашивает у root-сервера: «кто отвечает за зону .com?»
4
TLD-сервер зоны .com. Возвращает адрес авторитетного сервера для google.com.
5
Авторитетный сервер. Хранит реальную запись: google.com = 142.250.184.78.
6
Ответ возвращается резолверу и браузеру. Резолвер и браузер кешируют его на TTL, указанный в записи (минуты или часы).

Без кеша полный цикл занимает 20-120 миллисекунд. С прогретым кешем DNS-запрос укладывается в миллисекунды и часто не выходит дальше резолвера провайдера.

TCP

Соединение перед отправкой данных

HTTP-запрос не выкидывают в сеть наугад. Сначала клиент и сервер устанавливают TCP-соединение через трёхстороннее рукопожатие.

браузер
сервер

TCP гарантирует: все байты доходят, в правильном порядке, без дубликатов. Потерянный пакет переотправляется автоматически. Рукопожатие занимает один RTT (round-trip time), обычно 10-100 мс.

TLS

TLS-рукопожатие при HTTPS

После TCP, если адрес начинается с https://, выполняется ещё один обмен: TLS-рукопожатие. Цель: договориться о ключе шифрования и проверить, что сервер действительно тот, за кого себя выдаёт.

1
ClientHello. Браузер отправляет список поддерживаемых алгоритмов шифрования и случайное число.
2
ServerHello + сертификат. Сервер выбирает алгоритм и присылает свой TLS-сертификат с публичным ключом.
3
Проверка сертификата. Кто его выдал (Let's Encrypt, DigiCert и т. п.), для какого домена и не истёк ли он. Браузер сверяется со встроенным списком доверенных центров.
4
Обмен ключами. Стороны выводят общий симметричный ключ. Дальше всё содержимое шифруется этим ключом.
Защищённый канал готов. Поверх него уходит обычный HTTP-запрос, но снаружи виден только шифр.

Если сертификат не проходит проверку (не тот домен, истёк, выдан неизвестным центром), браузер показывает страницу с предупреждением и не пускает дальше. Это защита от подмены сервера.

HTTP

Stateless: сервер не помнит

Каждый запрос независим. Сервер не помнит предыдущий.

запрос #1

запрос #3

Версии

Три поколения HTTP

HTTP/1.1

1997
  • текстовый протокол, читается человеком
  • одно TCP-соединение, один запрос в момент времени
  • для параллельности браузер открывает 6 соединений на хост
  • база, на которой учат HTTP

HTTP/2

2015
  • бинарный фрейминг, быстрее парсится
  • мультиплексирование: десятки параллельных запросов в одном соединении
  • сжатие заголовков (HPACK)
  • сейчас на нём большая часть веба

HTTP/3

2022
  • работает поверх QUIC, а не TCP
  • TLS встроен в протокол, рукопожатие быстрее
  • потеря одного пакета не блокирует остальные потоки
  • заметно лучше на нестабильном Wi-Fi и мобильной сети

Семантика (методы, статусы, заголовки) одинаковая во всех трёх версиях. Версию выбирают браузер и сервер во время TLS-рукопожатия. В DevTools на вкладке Network видно, какая используется на каждом запросе.

Проблема

HTTP идёт в открытом виде

Вы в кафе, логинитесь на сайте. Все между вами и сервером могут прочитать ваш пароль.

клиент
сервер

Решение

HTTPS = HTTP + TLS

клиент
сервер
  • Шифрование: посередине никто не прочитает
  • Аутентификация: сертификат подтверждает, что это реально bank.com
  • Целостность: данные нельзя поменять незаметно

HTTPS

Что шифруется, а что нет

Скрыто шифрованием
  • +стартовая строка (GET /users/42)
  • +заголовки, включая Authorization и Cookie
  • +тело запроса и ответа
Остаётся видимым
  • !домен назначения (через SNI)
  • !IP-адрес сервера
  • !размер передаваемых данных

Провайдер и точка Wi-Fi видят, с каким сайтом вы соединились. Что именно вы там делали, при HTTPS им недоступно.

Вопрос аудитории

Что увидит перехватчик трафика?

Вы открыли https://bank.com/account/balance в публичном Wi-Fi кафе. Человек с ноутбуком в той же сети снифит трафик через Wireshark.

  • А) Полный URL с путём /account/balance, заголовки и тело ответа в открытом виде
  • Б) Только то, что вы соединились с доменом bank.com, его IP-адрес и размер передаваемых данных
  • В) Ничего. HTTPS скрывает даже факт соединения

Подумайте, какие именно слои защищает TLS. Ответ на следующем слайде.

Ответ

Б: виден только домен, IP и размер

  • TLS шифрует всё содержимое HTTP: стартовую строку, заголовки (включая Cookie и Authorization) и тело.
  • Путь /account/balance и форма с паролем будут зашифрованы и недоступны для чтения.
  • Имя домена при подключении передаётся в открытом виде в TLS-расширении SNI, чтобы сервер понял, чей сертификат отдавать.
  • IP-адрес назначения видно на сетевом уровне, его не спрятать без VPN или Tor.
  • Размер пакетов и время отправки тоже видны, по ним иногда восстанавливают тип действия (метаданные).

Поэтому совет «не вводи пароль в кафе» при HTTPS звучит уже устаревше. Пароль защищён. Но провайдер всё ещё знает, на какие сайты вы заходите.

Зачем нужен query

Путь говорит «куда идти» на сервере. Query говорит «что именно хочу». Когда вы заходите на сайт поиска, путь это /search, а query это «найди слово python, страница 2, по 20 результатов на странице».

/search?q=python&page=2&limit=20

куда идём на сервере

начало query
q=python

&

page=2

Формула всегда одна: ?ключ=значение&ключ=значение&ключ=значение. Знак = разделяет имя параметра и его значение, & разделяет сами параметры.

Query в реальных сайтах

Такие URL вы видите каждый день в адресной строке. Что после ? это и есть query-параметры конкретного сайта.

q = поисковый запрос, hl = язык интерфейса, num = сколько результатов на странице.

Вопрос аудитории

Какая часть URL не доходит до сервера?

Вы открываете в браузере такой адрес:

https://example.com:443/articles/42?sort=new#comments

Какие из этих частей сервер фактически не получает в HTTP-запросе?

  • А) :443 (порт)
  • Б) ?sort=new (query-параметры)
  • В) #comments (фрагмент)

Ответ

В: фрагмент #comments остаётся в браузере

  • Фрагмент после # используется браузером для скролла к якорю на странице. На сервер он не отправляется.
  • Порт 443 сервер «получает» косвенно: на нём он слушает TCP-соединение. В сам HTTP-запрос порт не пишется, но без него браузер не знал бы, куда стучаться.
  • Query-параметры приходят целиком в стартовой строке: GET /articles/42?sort=new HTTP/1.1.
GET /articles/42?sort=new HTTP/1.1 Host: example.com # фрагмента здесь нет

Практический вывод: серверная аналитика не видит, к какой секции страницы перешёл пользователь. Для трекинга фрагментов нужно слать его отдельным запросом из JavaScript.

Сравнение

GET и POST

GET

Данные в URL

GET /search?q=python&page=2 HTTP/1.1 Host: api.com

Тела нет. Для чтения.

POST

Данные в теле

POST /users HTTP/1.1 Host: api.com Content-Type: application/json {"name": "Alice", "age": 30}

URL чистый. Для создания.

Сравнение

PUT vs PATCH

PUT: замена целиком
{"id": 42, "name": "Alice", "email": "a@x.com", "age": 30} PUT /users/42 {"name": "Alice", "email": "new@x.com"} # результат: {"id": 42, "name": "Alice", "email": "new@x.com"}
PATCH: частичное обновление
{"id": 42, "name": "Alice", "email": "a@x.com", "age": 30} PATCH /users/42 {"email": "new@x.com"} # результат: {"id": 42, "name": "Alice", "email": "new@x.com", "age": 30}

PUT отправляет полную новую версию. PATCH говорит «поменяй только эти поля». На практике многие API делают PUT как PATCH, всегда проверяйте документацию.

Вопрос аудитории

Двойной клик из-за плохого Wi-Fi

Пользователь нажимает кнопку «Создать заказ», страница долго думает, он нервничает и нажимает ещё раз. Запрос ушёл дважды. С каким методом это создаст реальную проблему?

  • А) GET /orders/42 (получить данные о заказе)
  • Б) POST /orders (создать новый заказ)
  • В) DELETE /orders/42 (удалить заказ)

Вспомните таблицу методов и колонку «идемпотентный».

Ответ

Б: POST создаст два заказа

  • POST не идемпотентный. Каждый вызов создаёт новый ресурс. Два запроса = два заказа в базе и два списания.
  • GET только читает. Повторный вызов вернёт те же данные, побочных эффектов нет.
  • DELETE идемпотентный по спецификации: после второго вызова заказ уже удалён, состояние то же. Сервер обычно отвечает 204 No Content или 404 Not Found.

Как защититься на стороне клиента: блокировать кнопку после клика до получения ответа. На стороне сервера: использовать idempotency key, уникальный заголовок, по которому второй запрос с тем же ключом возвращает результат первого, а не создаёт ещё один заказ.

POST /orders HTTP/1.1 Idempotency-Key: 7a4f9c1e-2b3d-4a5b-9e8f-6c7d8e9f0a1b Content-Type: application/json {"product_id": 42, "qty": 1}

Вопрос аудитории

Получили 403 Forbidden: поможет ли релогин?

Пользователь залогинился, токен лежит в localStorage. При попытке открыть чужой проект сервер отвечает 403. Стоит ли разлогинить пользователя и попросить войти заново?

  • А) Да. Новый токен решит проблему
  • Б) Нет. Токен валидный, но прав на этот проект всё равно нет
  • В) Сначала попробовать обновить токен, если не помогло: разлогинить

Ответ

Б: токен ни при чём, прав нет

  • 401 Unauthorized = «я тебя не знаю или твой токен невалиден». Имеет смысл попробовать обновить токен или попросить логин.
  • 403 Forbidden = «я тебя знаю, но сюда тебе нельзя». Релогин не изменит права. Это решение со стороны бэкенда.
  • Правильная реакция фронтенда: показать понятное сообщение «нет доступа к ресурсу», предложить вернуться. Принудительный разлогин ухудшит UX и не решит задачу.

Запомнить можно так: на 401 чините авторизацию, на 403 чините права (роли, доступ к ресурсу), на 404 ресурса вообще нет. Иногда сервер намеренно отвечает 404 вместо 403, чтобы не подтверждать существование закрытого ресурса.

REST

Что такое REST и REST API

REST это набор договорённостей, как проектировать API поверх HTTP. Не язык, не библиотека, не протокол. Когда говорят «REST API», имеют в виду API, написанный по этим договорённостям.

REST

REpresentational State Transfer

Стиль архитектуры распределённых систем. Описывает, как сервер должен отвечать на запросы клиента, опираясь на готовые механизмы HTTP: URL, методы, статусы, заголовки.

Описал Рой Филдинг в диссертации 2000 года.

REST API

API, который следует REST

Каждая «вещь» в системе (пользователь, заказ, пост) это ресурс. У ресурса свой URL. Действия выражаются методами HTTP, а не глаголами в URL.

На практике 90% публичных HTTP-API сделаны в REST-стиле.

Не REST
POST /getUserById?id=42
POST /createUser
POST /deleteUser?id=42
POST /searchPosts?q=python

действие зашито в путь, метод почти всегда POST

REST

в URL только существительные, действие задаёт HTTP-метод

Главная идея: сущности в URL, действия в методах. Зная это правило, программист угадывает, как обратиться к новому API ещё до того, как откроет документацию.

requests · Python

Обработка ошибок и timeout

try: response = requests.get(url, timeout=10) response.raise_for_status() data = response.json() except requests.exceptions.Timeout: print("Не ответил за 10 секунд") except requests.exceptions.ConnectionError: print("Нет соединения") except requests.exceptions.HTTPError as e: print(f"HTTP ошибка: {e.response.status_code}")

Главное правило: всегда ставьте timeout. Без него запрос может висеть бесконечно, забивая воркеры.

Хранилище

Где браузер хранит токены и данные

Аутентификационный токен где-то лежит между запросами. В современном фронтенде есть несколько хранилищ, у каждого свои правила.

Хранилище Видимость и время жизни Когда использовать
Cookie браузер прицепляет к каждому запросу к домену автоматически. Сервер ставит через Set-Cookie. Флаг HttpOnly прячет от JS, Secure ограничивает HTTPS. Размер до 4 КБ. сессии, серверный auth, трекинг
localStorage доступен только JavaScript. Не отправляется с запросами сам. Сохраняется при закрытии вкладки. До 5-10 МБ. JWT-токены, настройки UI
sessionStorage как localStorage, но очищается при закрытии вкладки. Те же 5-10 МБ. состояние одной сессии работы
IndexedDB полноценная встроенная база данных. Асинхронный API, индексы, транзакции. большие объёмы, оффлайн-данные
Cache API хранит HTTP-ответы. Используется Service Worker'ами для оффлайн-режима. PWA, фоновая синхронизация

Bearer-токены обычно держат в localStorage: JS читает токен и сам подкладывает в Authorization. Сессионные cookies браузер цепляет автоматически, и при флаге HttpOnly JS даже не видит их значения, что снижает риск кражи через XSS.

Вопрос аудитории

Где хранить токен, чтобы XSS его не украла?

XSS-уязвимость: это когда злоумышленник умеет выполнить свой JavaScript на странице вашего сайта. Какой вариант хранения токена защитит его в этой ситуации?

  • А) localStorage.setItem("token", "...")
  • Б) Cookie без флагов
  • В) Cookie с флагами HttpOnly и Secure

Ответ

В: cookie с HttpOnly и Secure

  • HttpOnly запрещает JavaScript читать значение cookie. Чужой скрипт не получит токен через document.cookie.
  • Secure разрешает отправлять cookie только по HTTPS. Через обычный HTTP браузер его не приложит.
  • localStorage доступен любому скрипту на странице. XSS читает токен одной строкой localStorage.getItem("token").
  • Cookie без флагов тоже читается из JS и уходит даже по HTTP, защиты практически нет.

Полная защита от XSS это всё-таки не допустить XSS: экранировать пользовательский ввод, использовать CSP, проверять зависимости. HttpOnly снижает ущерб, если XSS всё же случилась, но не отменяет необходимость её предотвращать.

# Со стороны сервера: Set-Cookie: session=eyJhbGc...; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400

Пагинация

Зачем нужна пагинация

Без пагинации

Сервер пытается отдать миллион пользователей одним ответом. Память, сеть, время, всё в красной зоне.

С пагинацией

Сервер отдаёт порциями по 20. Клиент сам решает, когда запросить следующую страницу.

Пагинация

Четыре подхода

1. Offset / Limit

?offset=20&limit=20

Самый частый. Медленный на больших offset.

2. Page-based

?page=2&per_page=20

Понятный пользователю. Те же проблемы что у offset.

3. Cursor-based

?cursor=eyJpZCI6MTAwfQ

Стабильно при изменениях. Нельзя «перепрыгнуть» на страницу.

4. Link headers

Link: <...?page=3>; rel="next"

Самодокументируемый (GitHub). Нужно разбирать заголовок.

Вопрос аудитории

Скрипт получил 429 Too Many Requests

Ваш скрипт делает запросы к API в цикле. На 500-м запросе сервер впервые отвечает 429. Что лучше сделать?

for user_id in user_ids: response = requests.get(f"https://api.example.com/users/{user_id}", timeout=10) response.raise_for_status() process(response.json())
  • А) Игнорировать. raise_for_status() бросит исключение, пользователь увидит ошибку и перезапустит
  • Б) Подождать (например, time.sleep) и повторить запрос. При повторных 429 увеличивать паузу
  • В) Открыть второе соединение в параллель, чтобы быстрее «дожать» оставшиеся запросы

Ответ

Б: подождать и повторить с увеличением паузы

  • 429 это явный сигнал «помедленнее». Сервер не сломан, он защищается от перегрузки. Обычная практика: backoff и retry.
  • Часто сервер указывает заголовок Retry-After в секундах или дате. Используйте его, если он есть.
  • Без Retry-After применяют exponential backoff: 1с, 2с, 4с, 8с, с верхним пределом, плюс случайный «jitter».
  • Открывать дополнительные соединения только ускорит блокировку. Серверы лимитируют по IP или по токену.
import time, random def get_with_retry(url, max_attempts=5): for attempt in range(max_attempts): r = requests.get(url, timeout=10) if r.status_code != 429: return r wait = int(r.headers.get("Retry-After", 2 ** attempt)) time.sleep(wait + random.uniform(0, 1)) # jitter r.raise_for_status()

Best practices

Семь правил

  • Читай документацию до того, как писать код
  • Всегда ставь timeout
  • Уважай rate limits, получил 429 подожди
  • Retry с exponential backoff на 5xx
  • Не доверяй структуре ответа: .get() лучше []
  • Логируй запросы
  • Тестируй на sandbox перед продакшеном
