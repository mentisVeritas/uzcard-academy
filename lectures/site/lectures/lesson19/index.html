Источники · Подробно

Что такое (транзакционная) База данных?

Её также называют OLTP - Online Transaction Processing. "Транзакционная" значит, что она надёжно обрабатывает поток крошечных, точных чтений и записей в реальном времени: пользователь нажимает "купить", и прямо сейчас записывается одна строка. Каждое действие сначала попадает сюда.

Примеры: PostgreSQL · MySQL (веб-приложения) · Oracle · SQL Server (банки, корпорации) · MongoDB (профили) · DynamoDB (большой масштаб) · Redis (корзины, сессии). Почему это источник: каждая транзакция сначала попадает сюда. Мы копируем её наружу - обычно через CDC - потому что прямой запуск аналитики заблокировал бы строки и замедлил живое приложение.

Источники · База данных

OLTP против OLAP - две задачи, две базы данных

Каждая база данных создана для одной из двух задач. Живое приложение использует одну; аналитика - другую. Именно из-за этого разделения и существует весь конвейер.

OLTP · источник

Online Transaction Processing

Живая операционная БД - поток крошечных, точных записей в реальном времени. Хранит текущее состояние. Здесь данные рождаются.

PostgreSQL · MySQL · Oracle
OLAP · хранилище

Online Analytical Processing

Аналитическая БД - несколько огромных запросов по миллиардам строк истории. Здесь данные анализируются (Часть 4).

Snowflake · BigQuery · Redshift
OLTP (источник)OLAP (хранилище)
Задачаобслуживать живое приложениеанализировать данные
Запросыкрошечные, миллионы/секогромные, по нескольку за раз
Затрагиваетпо одной строке за размиллиарды строк сразу

Аналитику никогда не запускают на OLTP - это заблокировало бы строки и замедлило живое приложение. Поэтому data engineering копирует данные в OLAP-хранилище. Это копирование и есть весь конвейер.

Источники · База данных

Реляционные против нереляционных

Мы только что разделили базы по задаче (OLTP против OLAP). Они также делятся по структуре - как данные устроены внутри. Это отдельный вопрос, и именно поэтому наши источники включают не только обычные SQL-таблицы.

Реляционные · SQL

Таблицы со связями

Фиксированные столбцы и строки, внешние ключи связывают таблицы. Запросы на SQL. Строгая согласованность, полный ACID.

PostgreSQL · MySQL · Oracle · SQL Server
Нереляционные · NoSQL

Гибкие структуры

Нет фиксированной схемы. Документы, пары ключ-значение, широкие столбцы или графы. Создано, чтобы гнуться и масштабироваться.

MongoDB (документы) · Redis (ключ-значение) · DynamoDB · Cassandra · Neo4j (граф)

"Реляционная" - это то же, что OLTP? Нет - это независимые оси. Большинство OLTP-баз реляционные (PostgreSQL), но не все (MongoDB, Redis); OLAP-хранилище почти всегда реляционное. Так что источник может быть любым сочетанием: PostgreSQL = реляционная + OLTP · MongoDB = нереляционная + OLTP · BigQuery = реляционное + OLAP. Поэтому наш конвейер должен уметь работать с обеими формами.

Источники · База данных

ACID - что делает базу данных надёжной

Четыре гарантии, которые транзакционная (OLTP) база даёт каждой записи. Поэтому деньги, заказы и входы хранятся в PostgreSQL - а не в лог-файле.

A

Atomicity (атомарность)

Всё или ничего. Перевод двигает деньги полностью или совсем не двигает - никогда наполовину.

C

Consistency (согласованность)

Данные всегда остаются корректными - каждое правило и ограничение выполняется после каждой транзакции.

I

Isolation (изоляция)

Параллельные транзакции не мешают друг другу. Двое покупают одновременно - всё остаётся верным.

D

Durability (надёжность)

После коммита данные не теряются - они переживают сбои и отключение питания.

Почему это важно: ACID обходится дорого - на каждую запись это блокировки, обновление индексов и проверки. Идеально для заказов и платежей. Но это именно то, что не нужно для шквала сырых событий - поэтому Kafka отбрасывает это ради скорости. Об этом дальше.

Источники · Подробно

Что такое Kafka (очередь сообщений)?

Труба для событий в реальном времени. Производители пишут события, потребители их читают - миллионы в секунду, по порядку, с возможностью перечитать.

Пример: Uber использует Kafka для живых GPS-сигналов каждого водителя. Главная идея: одно событие может питать сразу много потребителей - lake его хранит, антифрод проверяет его на лету, дашборд его считает. Всё за миллисекунды.

Источники · Kafka против БД

Как Kafka хранит данные - лог только на дозапись

Kafka - это не база данных. Она хранит события как последовательный лог на диске - каждое новое событие дописывается в конец с номером, его offset. Без таблиц, без столбцов, без индексов.

offset 0 → { "user":41, "event":"click", "page":"/home" }
offset 1 → { "user":88, "event":"click", "page":"/checkout" }
offset 2 → { "user":41, "event":"buy", "item":"shoes" }
offset 3 → { "user":99, "event":"click", "page":"/home" }
… просто растущий список, дозаписываемый в конец

Только дозапись

События неизменяемы - нет UPDATE, нет DELETE. Записал один раз, читают многие.

Временно

Окно хранения (например, 7 дней), затем автоудаление. Труба, а не постоянное хранилище.

Партиционирование

Каждый топик разбит на множество машин-брокеров → миллионы/сек параллельно.

Поток: Kafka (временная труба, ~7 дней) → потребитель читает → Data Lake / S3 (постоянно, навсегда). Kafka - это магистраль; S3 - склад в конце пути.

Источники · Kafka против БД

Почему не писать события прямо в PostgreSQL?

Крупное приложение генерирует 500 000+ кликов/сек. Postgres рассчитан на тысячи записей/сек - он рухнет и потянет за собой живое приложение (заказы, платежи, входы).

На каждую запись…PostgreSQLKafka
Обновить индексыДа (медленно)Нет индексов
Проверить ограниченияДаНет
Блокировать строкиДаБез блокировок
UPDATE / DELETEРазрешеныНеизменяемо
Гарантии ACIDПолныеНе нужны
Шаблон записиСлучайный (куда угодно)Последовательный (в конец)

Аналогия: PostgreSQL = картотека - найти, обновить, сопоставить любой документ, но медленно добавлять миллион файлов в секунду. Kafka = конвейерная лента - быстрая именно потому, что делает меньше. Последовательная запись на диск в 10-100× быстрее случайной. Философия Kafka: не быть базой данных, быть самой быстрой трубой в мире.

Источники · Kafka против БД

Почему эти различия дают скорость

"Нет индексов, нет блокировок" звучит абстрактно. Вот во что каждое из них реально обходится - и почему отказ от него позволяет Kafka лететь.

Что такое индекс?

Как указатель в конце книги - отсортированный поиск, чтобы база быстро находила строку. Но каждая запись обязана ещё и обновить этот индекс. Лишняя работа, каждый раз. Kafka не держит ни одного.

Что такое блокировка?

Чтобы оставаться корректным, Postgres блокирует строку на время записи, чтобы две записи не столкнулись - остальные ждут своей очереди. Kafka не блокирует никогда: события просто складываются в конец, и ничто не ждёт.

Случайная против последовательной

Postgres скачет по диску, обновляя строки и индексы (случайные записи). Kafka только дописывает в конец (последовательно) - самое быстрое, что умеет диск, в 10-100× быстрее.

Складываем: нет обновления индексов + нет блокировок + запись только в конец = Kafka тянет миллионы/сек, а Postgres - тысячи. Тот же диск, гораздо меньше работы на событие. В этом весь фокус.

Источники · Подробно

Что такое Логи?

Текстовые записи с метками времени, которые системы пишут о том, что они делают - каждый запрос, ошибка и событие, строка за строкой.

Примеры

Логи веб-серверов (Nginx, Apache) · логи ошибок приложений · логи аудита (кто к чему обращался) · логи CDN (Cloudflare) · облачные логи (AWS CloudTrail, Kubernetes)

Зачем они нужны

Часто это единственная запись о поведении, которое так и не попало в базу - неудавшиеся запросы, замедления, точный путь перед сбоем или оттоком. Отправляются в lake / Splunk / ELK / Datadog.

Источники · Подробно

Что такое сторонние / внешние данные?

Данные, которые возникают полностью вне вашей компании - вы их не создавали, вы их приобрели или получили.

Примеры

Рыночные и FX-потоки (Bloomberg, Reuters) · кредитные бюро (Katm) · обогащение (Clearbit, ZoomInfo) · открытые данные (перепись, погода) · файлы партнёров через SFTP.

Зачем они нужны

Ваши собственные данные описывают только ваш мир. Чтобы ответить "как мы выглядим на фоне рынка?" или "каков кредитный риск этого клиента?", нужен внешний контекст. Ноль контроля над качеством → валидируйте жёстко.

Местный пример: прежде чем банк в Узбекистане одобрит кредит, он подтягивает кредитную историю заявителя из национального кредитного бюро (Katm) и данные о карточных транзакциях из Uzcard / Humo - всё это сторонние данные, которыми банк не владеет, не может контролировать и обязан проверить, прежде чем им доверять.

Загрузка · Потоковая

Потоковая: из Kafka на вашу платформу

Kafka только хранит события. Чтобы перенести их в Lake или Warehouse, нужен потоковый обработчик - он читает Kafka, при необходимости преобразует и пишет в место назначения.

Flink

Самый мощный. Соединения и агрегации пока данные движутся. Uber, Netflix, Alibaba.

Kafka Connect

Встроенный. Только конфиг "читай топик → выгружай в S3". Типичный шаг Kafka → Bronze.

Kinesis (AWS)

Kafka от Amazon + нативная доставка в S3 / Redshift. Никаких лишних инструментов в AWS.

Spark Streaming

Spark в микро-пакетах (каждые несколько секунд). Используете уже знакомые навыки.

Ключевая мысль: большинство компаний стримят только в Lake (Kafka → Kafka Connect → S3), а оттуда уже пакетно через Airflow + dbt. Полноценный сквозной стриминг прямо в DWH оставляют для живого фрода и дашбордов реального времени - его гораздо сложнее поддерживать.

Загрузка · CDC

CDC - Change Data Capture

Живая база данных меняется каждую секунду. Как скопировать в хранилище каждое изменение - включая удаления - не запуская тяжёлых запросов на живом приложении? Вы читаете собственный журнал изменений базы.

1 · WAL

Каждая база уже ведёт внутренний Write-Ahead Log - запись каждого изменения для собственного восстановления после сбоев. CDC просто подключается к нему.

2 · Читатель следит за ним

Инструмент вроде Debezium отслеживает этот журнал. Он никогда не запускает запросов, поэтому нулевая дополнительная нагрузка на живую базу.

3 · Стримим наружу

Каждое изменение становится событием → Kafka → ваш Lake / Warehouse, почти в реальном времени.

Почему не перезапрашивать таблицу? Запрос вроде WHERE updated_at > last_run нагружает живую базу, требует столбца с меткой времени и не видит удалённых строк - их просто нет. Журнал показывает всё, поэтому CDC ловит вставки, обновления и удаления.

Загрузка · CDC

CDC в реальном мире

Одна кредитная заявка в основной системе банка. Посмотрим, как одна строка меняется в течение дня - и как CDC мгновенно держит аналитическое хранилище в синхроне.

ВремяИзменение в живой БД (OLTP)CDC стримит в хранилище
09:00INSERT · новая заявка, статус submittedстрока добавлена, за секунды
11:30UPDATE · статус → under_reviewстрока обновлена
14:00UPDATE · статус → approvedстрока обновлена
след. деньDELETE · заявитель отменяетстрока удалена

Без CDC ночной пакет делает один снимок и фиксирует только "approved" - он пропускает дневные шаги и никогда не видит отмену, оставляя призрачный одобренный кредит в каждом отчёте и риск-модели. С CDC все четыре изменения стримятся по мере появления, и хранилище всегда соответствует реальности.

Хранение · Основы

Три формы данных

Прежде чем выбирать, где хранить данные, узнайте их форму - именно она решает, где они могут жить.

Структурированные

Хранение · Подробно

Что такое Data Lake?

Огромное, дешёвое хранилище-бакет, которое держит любые файлы в любом формате - сырые, необработанные.

✓ Сильные стороны

Крайне дёшево (~$23/ТБ/месяц). Хранит что угодно. Идеально для сырых ML-данных, изображений, файлов моделей.

✗ Слабые стороны

Схема не навязывается. Нет ACID. Без управления превращается в "болото данных", в котором никто не разберётся.

Примеры: AWS S3, Google Cloud Storage, Azure Data Lake. Аналогия: гигантский гараж - можно закинуть что угодно, но без меток вы больше ничего не найдёте.

Хранение · Подробно

Что такое Data Warehouse?

База данных, созданная только для аналитики - структурированные таблицы, строгая схема, молниеносный SQL по миллиардам строк.

Колоночное

Читает только запрашиваемые столбцы - в 10× быстрее строкового хранения.

Строгая схема

Каждый столбец типизирован. Данные остаются чистыми и надёжными.

Массовый параллелизм

Агрегаты по миллиарду строк за секунды.

Примеры: Snowflake, Google BigQuery, Amazon Redshift. Аналогия: идеально организованная библиотека - всё каталогизировано, расставлено по полкам, мгновенно находится, но хранит только "книги" (структурированные данные), а не изображения или видео. Главное: это отдельная аналитическая копия (OLAP) - не живая база приложения (OLTP), откуда пришли данные. Те же данные, другая система, противоположная задача.

Хранение · Подробно

Что такое Lakehouse?

Современное сочетание: хранилище Lake (дёшево, любой формат) + возможности Warehouse (ACID, схема, быстрый SQL) в одной системе.

Примеры: Databricks, Snowflake + Iceberg. Суперсила для DS - путешествие во времени: SELECT * FROM orders VERSION AS OF '2024-01-01' - точно воспроизвести любой прошлый эксперимент.

Часть 5 · Приближаем

Преобразование

Превращаем сырые данные в чистые, надёжные, готовые для бизнеса таблицы - ETL/ELT и паттерн Bronze→Silver→Gold

Преобразование · ETL против ELT

Где происходит "преобразование"?

ETL - старый подход

Extract → Transform → Load

Преобразование на отдельном сервере до загрузки. Сырые данные потом выбрасываются.

✗ Ошибка = история потеряна навсегда
✗ Дорогие выделенные серверы
ELT - современный ✓

Extract → Load → Transform

Сначала загрузить сырьё, преобразовать внутри хранилища с помощью SQL. Сырьё всегда сохраняется.

✓ Ошибка? Поправь SQL, перезапусти
✓ dbt = преобразования под версионным контролем

Пример - одна ошибка, два исхода: через месяц вы обнаруживаете, что выручка суммировалась неверно. При ETL сырые заказы преобразовали и выбросили - прошлого нет, можно поправить только на будущее. При ELT сырьё всё ещё лежит в Bronze - поправьте одну строку SQL, перезапустите, и каждый прошлый месяц исправляется мгновенно. Вот почему победил ELT.

Преобразование · Medallion

Bronze → Silver → Gold

Данные очищаются в три слоя - каждый чище и полезнее предыдущего.

🥉 Bronze

Сырьё, как есть

Точная копия из источника. Пустые значения, дубли, неверные типы - всё сохранено. Никогда не удаляется.

raw_orders · raw_users
🥈 Silver

Очищено и соединено

Типизировано, без дублей, соединено по источникам. Надёжные строки.

stg_orders · stg_customers
🥇 Gold

Готово для бизнеса

Агрегировано, применена бизнес-логика. Именно это вы и запрашиваете.

fct_daily_revenue · dim_customers

Правило DS: Вы работаете на уровне Gold. Если Gold неверен → проверьте Silver. Если Silver неверен → Bronze всегда хранит истину.

Преобразование · dbt

dbt - преобразования как SQL под версионным контролем

dbt (Data Build Tool) позволяет писать каждое преобразование как обычный SQL-файл. Он работает внутри вашего хранилища и очищает данные Bronze → Silver → Gold.

models/gold/daily_revenue.sql
-- Gold: одна строка на день
select
  order_date,
  sum(amount) as revenue
from {{ ref('stg_orders') }}
group by order_date

Под версионным контролем

Каждая модель живёт в Git - просматривайте, откатывайте, видите, кто что менял.

С тестами

Встроенные тесты данных: not-null, unique, допустимые значения, ссылочная целостность.

С документацией

Автогенерируемая документация и граф происхождения каждой создаваемой таблицы.

Где его место: dbt - это шаг Преобразование, Silver → Gold. Airflow планирует его; dbt делает SQL. Метрика неверна? Поправьте SQL, перезапустите, и весь граф зависимостей пересобирается сам.

Часть 6 · Приближаем

Оркестрация

Дирижёр, который запускает каждый шаг по порядку, по расписанию и обрабатывает сбои

Оркестрация · Airflow

Что такое DAG?

Конвейер, нарисованный как граф: задачи (блоки) с зависимостями (стрелки). Airflow запускает их по порядку, перезапускает сбои, оповещает команду.

Без оркестрации: конвейеры крутятся как cron-задачи, которые никто не отслеживает, сбои остаются незамеченными, плохие данные доходят до вашей модели. С Airflow: зелёный/красный статус, автоповторы, оповещения в Slack. Инструменты: Airflow, Dagster, Prefect.

Оркестрация · Airflow

Что на самом деле делает оркестратор

Запуск задач по порядку - это только начало. В этом разница между хрупким скриптом и продакшен-конвейером, которому можно доверять в 3 часа ночи.

Расписание

Запускается по таймеру - каждую ночь в 3:00, без участия человека.

Зависимости

Задача B ждёт задачу A. Это и есть DAG - порядок гарантирован.

Повторы

Нестабильная задача автоматически повторяется, прежде чем сдаться. Сбои самоустраняются.

Backfill

Перезапуск любой прошлой даты, чтобы исправить ошибку или заполнить пробел в истории.

И он следит за всем: живой зелёный/красный дашборд с оповещениями в Slack или по email в момент сбоя задачи - чтобы плохие данные никогда незаметно не дошли до вашей модели. Инструменты: Airflow · Dagster · Prefect.

Оркестрация · Качество

Ловим плохие данные до того, как они дойдут до вас

5 проверок качества

Схема - столбец исчез или сменился тип?
Свежесть - таблица обновилась вовремя?
Распределение - резко вырос процент пустых значений?
Ссылочная целостность - висячие внешние ключи?
Бизнес-правила - выручка < 0? возраст = 450?

Тихий сбой

Конвейер показывает зелёный ✓. Завершился вовремя. Но загрузил 0 строк из-за изменения схемы выше по потоку.

Дашборд показывает $0 выручки. Ваша модель переобучается на пустоте - и днями никто этого не замечает.
