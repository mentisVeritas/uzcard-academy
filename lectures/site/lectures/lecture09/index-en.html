It is an approach where code is written under the assumption that "everything may go wrong": the network goes down, the DB lags, the partner API returns garbage, someone types something wrong.

Exception basics

What is an exception

An exception is the "something went wrong" signal Python sends when it cannot perform an operation. Without handling, the program crashes.

data = {"name": "Aziz", "balance": 350_000} # Trying to access a non-existent key value = data["account_id"] # Python raises an exception here print("This line is never executed")
Traceback (most recent call last): File "demo.py", line 5, in <module> value = data["account_id"] KeyError: 'account_id'

Python created a KeyError object, nobody handled it, the program crashed with a Traceback.

Exception basics

How to read a traceback

A traceback is read bottom-up. The last line: the essence of the problem. The lines above: how we got there.

def extract_rate(api_response: dict) -> float: return float(api_response["data"]["rate"]) def calculate_amount(amount_uzs: float, api_response: dict) -> float: rate = extract_rate(api_response) return amount_uzs / rate def process_order(order: dict) -> float: cbu_response = { "status": "OK", "data": {"exchange_rate": 12550.0} # the key was renamed } return calculate_amount(order["amount"], cbu_response) process_order({"amount": 5_000_000.0})

Exception basics

Reading a traceback line by line

KeyError: 'rate' <-- WHAT failed File "demo.py", line 2, in extract_rate <-- WHERE it failed return float(api_response["data"]["rate"]) File "demo.py", line 6, in calculate_amount <-- WHO called it rate = extract_rate(api_response) File "demo.py", line 12, in process_order <-- higher up the stack return calculate_amount(order["amount"], cbu_response) File "demo.py", line 13, in <module> <-- entry point process_order({"amount": 5_000_000.0})

4Check what is inside api_response: it has exchange_rate, but we look for rate

Exception basics

try/except basic syntax

To catch an exception and prevent the program from crashing.

data = {"currency": "UZS", "amount": 350_000} try: value = data["currency_code"] # KeyError: no such key print(f"Got: {value}") # not executed except KeyError as e: print(f"Key not found: {e}") # this is executed print("Program continues running")
Key not found: 'currency_code' Program continues running

try wraps risky code, except catches a specific error type. The program does not crash.

Exception basics

Exception hierarchy: this is OOP too

In Python, exceptions are ordinary classes. KeyError inherits from LookupError, which in turn inherits from Exception. Each except SomeError works like isinstance(): it catches the class itself and any of its descendants.

# Base exceptions are defined like this: class BaseException: ... class Exception(BaseException): ... class LookupError(Exception): ... class KeyError(LookupError): ... # KeyError IS-A LookupError try: raise KeyError("key missing") except LookupError: # caught through the parent print("caught through the parent")
caught through the parent

Exception basics

Tree of standard exceptions

BaseException ├── SystemExit sys.exit() - do not catch ├── KeyboardInterrupt Ctrl+C - do not catch └── Exception everything that can be handled ├── ArithmeticError │ └── ZeroDivisionError division by zero ├── AttributeError obj.method() - no such method ├── LookupError │ ├── KeyError dict["missing"] │ └── IndexError list[999] ├── OSError │ └── ConnectionError │ └── ConnectionRefusedError ├── TypeError wrong type └── ValueError right type, wrong value

Do not catch BaseException: it includes SystemExit and KeyboardInterrupt. Otherwise you cannot even stop the program properly.

Exception basics

Exception object: useful attributes

An exception is an ordinary object. To write meaningful logs, it helps to know what is inside it.

def simulate_error(account_id: str) -> None: raise ConnectionRefusedError( f"PostgreSQL is unavailable. account_id={account_id}" ) try: simulate_error("UZ_ACC_9912") except ConnectionRefusedError as exc: print(f"Type: {type(exc).__name__}") print(f"Message: {exc}") print(f"args: {exc.args}")

Question for the audience

What does this code print?

try: raise KeyError("key missing") except Exception as e: print(f"[Exception] caught: {e}") except KeyError as e: print(f"[KeyError] caught: {e}")
  • A) [KeyError] caught: 'key missing'
  • B) [Exception] caught: 'key missing'
  • C) Both blocks are executed

Think for 30 seconds. The answer is on the next slide.

Answer

B: [Exception] caught

Python checks except blocks top-down and stops at the first match. KeyError is a descendant of Exception, so the first block catches the error and the second one is no longer executed.

Rule: from specific to general. Specific except's go on top, general ones at the bottom.

# Correct try: operation() except KeyError as e: # most specific first print(f"Key missing: {e}") except LookupError as e: # then the parent print(f"Lookup error: {e}") except Exception as e: # general at the end print(f"Unexpected error: {e}") # Wrong: Exception swallows everything try: operation() except Exception as e: # catches everything print(f"Error: {e}") except KeyError: # never executed ...

try/except in depth

Minimum code inside try

The less code in try, the more precisely you understand where it failed. Wrap only risky operations.

# Bad: the entire method is in try def bad_process(payload: dict) -> float | None: try: user_id = payload["user_id"] amount = float(payload["amount"]) currency = payload["currency"] return amount * 1.02 except Exception: return None # what failed and where - unclear # Good: each risky zone is separate def good_process(payload: dict) -> float | None: try: user_id = payload["user_id"] raw_amount = payload["amount"] currency = payload["currency"] except KeyError as missing: print(f"[REJECT] Missing field: {missing}") return None try: amount = float(raw_amount) except ValueError: print(f"[REJECT] Amount is not a number: '{raw_amount}'") return None return amount * 1.02

try/except in depth

Multiple except's: different errors, different reactions

A single except Exception for everything is one button for all situations. Granular except's allow different reactions.

Error typeReaction
Network down (Timeout)Retry after a few seconds
Invalid data (ValueError)Reject with code 422
Limit exceededNotify Compliance
Broken JSON from partnerLog, return PARTNER_ERROR

Python has no compiler safety net forcing exception handling, like Java does. You provide it yourself.

Example: Kapitalbank gateway

Question for the audience

What does process() return for a fraudulent transaction?

def check_fraud(tx: dict) -> bool: score = 8500 if scor > 9000: return True return False def process(tx: dict) -> dict: try: is_fraud = check_fraud(tx) return {"status": "BLOCKED" if is_fraud else "APPROVED"} except Exception: return {"status": "APPROVED"}
  • A) BLOCKED: antifraud worked correctly
  • B) APPROVED: antifraud did not run, program did not crash
  • C) The program crashes with NameError

Answer

B: APPROVED, antifraud did not run

  • scor is a typo. Python raises NameError: name 'scor' is not defined.
  • except Exception catches everything, including NameError.
  • The function returns APPROVED. The fraudster's transaction went through.

The most dangerous construct in this code. A broad except Exception without logging hides any bugs, including typos in the code.

# Correct solution def process(tx: dict) -> dict: try: is_fraud = check_fraud(tx) return {"status": "BLOCKED" if is_fraud else "APPROVED"} except KeyError as e: # expected error return {"status": "REJECTED", "reason": f"Missing field: {e}"} # NameError is not caught here, it flies out, # lands in the logs, on-call sees it and fixes the typo.

Rule: catch only what you expect and can handle.

try/except in depth

else block: runs only on success

A clean separation: "risky operation", "error handling" and "success code" live in different blocks.

try: risky_operation() # may raise an exception except SomeError: handle_error() # only when an exception occurs else: on_success() # only when no exception occurred finally: always() # runs in any case

If you put the "success code" inside try, except will catch its errors too and handle them like errors of the risky operation. That creates confusion in logs.

try/except in depth

else in practice: COMMIT only on success

class MockDB: def execute(self, query: str, params: dict) -> None: print(f" [SQL] {query[:40]}...") def commit(self) -> None: print(f" [SQL] COMMIT") def close(self) -> None: print(f" [SQL] Connection closed") def save_payment(db: MockDB, tx_data: dict) -> str | None: try: tx_id = tx_data["tx_id"] amount = float(tx_data["amount"]) if amount <= 0: raise ValueError(f"Amount must be > 0: {amount}") db.execute("INSERT INTO ledger ...", {"tx_id": tx_id, "amount": amount}) except KeyError as e: print(f"[EXCEPT] Missing field: {e}") return None except ValueError as e: print(f"[EXCEPT] {e}") return None else: print("[ELSE] Write succeeded, COMMIT") db.commit() return tx_id finally: print("[FINALLY] Closing the connection") db.close()

try performs the write, except catches errors, else commits the transaction, finally closes the connection in any case.

try/except in depth

else in practice: run and output

print("=== Success ===") save_payment(MockDB(), {"tx_id": "TX_001", "amount": "450000"}) print("=== Error ===") save_payment(MockDB(), {"tx_id": "TX_002", "amount": "-500"})
=== Success === [SQL] INSERT INTO ledger ... [ELSE] Write succeeded, COMMIT [SQL] COMMIT [FINALLY] Closing the connection [SQL] Connection closed === Error === [EXCEPT] Amount must be > 0: -500.0 [FINALLY] Closing the connection [SQL] Connection closed

On success: try → else → finally. On error: try → except → finally. The finally block runs in both cases.

try/except in depth

finally block: always runs

For guaranteed release of resources: closing a file, releasing a lock, closing a DB connection. finally runs even when try contains a return.

def deduct_funds(account_id: str, amount: float) -> str | None: print(f" [LOCK] Lock acquired for {account_id}") try: if amount > 5_000_000: raise ValueError("Limit exceeded") print(f" [OK] {amount} UZS deducted") return f"TX_{account_id}" # finally runs BEFORE return except ValueError as e: print(f" [ERROR] {e}") return None finally: print(f" [LOCK] Lock released for {account_id}") deduct_funds("UZ_5521", 500_000.0) deduct_funds("UZ_5521", 8_000_000.0)
[LOCK] Lock acquired for UZ_5521 [OK] 500000.0 UZS deducted [LOCK] Lock released for UZ_5521 [LOCK] Lock acquired for UZ_5521 [ERROR] Limit exceeded [LOCK] Lock released for UZ_5521

The lock is always released. Without finally the lock could have stayed forever.

Question for the audience

What does this code print?

def connect_to_db() -> None: try: raise ConnectionRefusedError("PostgreSQL is down") db_conn = {"session": "active"} except ConnectionRefusedError as e: print(f"[EXCEPT] {e}") finally: print("[FINALLY] Closing...") db_conn.close() connect_to_db()
  • A) Prints [EXCEPT], then [FINALLY] and exits silently
  • B) Prints [EXCEPT], [FINALLY], then crashes with UnboundLocalError
  • C) Prints only [EXCEPT], never reaches finally

Answer

B: UnboundLocalError on top of the original error

  • Inside try a ConnectionRefusedError was raised.
  • The line db_conn = ... was not executed, the variable does not exist.
  • except ran. finally called db_conn.close().
  • The variable is not defined. Python raises UnboundLocalError.
  • The new error overwrites the original one in the logs. On-call fixes the wrong thing.

Fix: initialize the resource with None BEFORE try.

def connect_to_db() -> None: db_conn = None # initialize BEFORE try try: raise ConnectionRefusedError("PostgreSQL is down") db_conn = {"session": "active"} except ConnectionRefusedError as e: print(f"[EXCEPT] {e}") return finally: if db_conn is not None: # safe check db_conn.close()

raise

Raising exceptions ourselves

raise translates business rules into the language of exceptions. Something syntactically correct can be a business error: amount = -50000, transfer to your own account, exceeding a limit.

MAX_TX = 10_000_000.0 # CBU limit def validate_payment(sender: dict, recipient: dict, amount: float) -> None: if amount <= 0: raise ValueError(f"Amount must be positive: {amount}") if sender["account_id"] == recipient["account_id"]: raise ValueError(f"Transfer to own account: {sender['account_id']}") if amount > MAX_TX: raise PermissionError(f"Amount {amount:,.0f} > limit {MAX_TX:,.0f}") if sender["balance"] < amount: raise ArithmeticError( f"Insufficient funds: requested {amount:,.0f}, balance {sender['balance']:,.0f}" ) sender = {"account_id": "UZ_A", "balance": 100_000.0} recipient = {"account_id": "UZ_B"} try: validate_payment(sender, recipient, 500_000.0) except (ValueError, PermissionError, ArithmeticError) as e: print(f"[{type(e).__name__}] {e}")
[ArithmeticError] Insufficient funds: requested 500,000, balance 100,000

Context managers

Problem: the resource was not closed

Every resource (file, connection, lock) must be closed after use. If an exception occurs between open and close, the f.close() line simply does not execute.

f = open("payments.txt", "r") data = f.read() int("abc") # ValueError raised here f.close() # this line does not run

This is a resource leak: the file is held, memory is not released. On a server with thousands of requests, such leaks pile up and bring down the process.

Context managers

What is with

with tells Python: "open this, let me work with it, and close it yourself even on error". Shorter and more reliable than try/finally.

via try/finally
f = open("payments.txt", "r") try: data = f.read() finally: f.close()
via with
with open("payments.txt", "r") as f: data = f.read() # close() is called automatically

A class with __enter__ and __exit__ methods works with with. __exit__ is always called, even when an exception occurs inside the block. That is the resource-release guarantee.

Context managers

How with works under the hood

The object passed to with must have two methods: __enter__ (entering the block) and __exit__ (leaving it). Python calls them for you.

with open("payments.txt") as f: | +-- 1. __enter__() opens the file, returns f | +-- 2. the body of the with block runs | | | +-- all OK __exit__() is called, file is closed | +-- exception raised __exit__() is called, file is closed, | then the exception keeps propagating | +-- 3. resource is released, guaranteed

The key value of with: __exit__() is always called. Even when an exception occurs inside the block, the resource is released.

Real examples

The same with syntax works for files, DBs, locks, sockets, temporary directories.

# Files with open("payments.txt", "r") as f: data = f.read() with open("report.txt", "w") as f: f.write("Transactions report") # Database import psycopg2 with psycopg2.connect(database="payments") as conn: with conn.cursor() as cursor: cursor.execute("SELECT * FROM transactions") rows = cursor.fetchall() # Thread lock import threading lock = threading.Lock() with lock: # only one thread at a time balance += amount

Context managers

Real example: a DB transaction

When working with a DB, with does two things at once: manages the transaction (commit on success, rollback on error) and closes the connection at the end.

import psycopg2 def transfer(from_id: str, to_id: str, amount: float) -> None: with psycopg2.connect(database="payments") as conn: with conn.cursor() as cur: cur.execute( "UPDATE accounts SET balance = balance - %s WHERE id = %s", (amount, from_id), ) cur.execute( "UPDATE accounts SET balance = balance + %s WHERE id = %s", (amount, to_id), ) # On exit from with: # success -> conn.commit(), cur.close(), conn.close() # error -> conn.rollback(), cur.close(), conn.close()

In a Celery background task the same construct guarantees that no hanging DB transactions and no unclosed connections remain between worker jobs.

Context managers

with and try/except together

with is responsible for resources, try/except for errors. They are usually used together.

try: with open("payments.txt", "r") as f: data = f.read() process(data) except FileNotFoundError as e: print(f"File not found: {e}") except ValueError as e: print(f"Processing error: {e}") # The file is closed in any case. # The exception is caught and handled.

The file is closed automatically, even when the exception is caught by the outer try/except block.

Context managers

DBTransaction: automatic COMMIT or ROLLBACK

class DBTransaction: def __init__(self, session_id: str): self.session_id = session_id def __enter__(self) -> "DBTransaction": print(f"[BEGIN] Session {self.session_id}") return self def __exit__(self, exc_type, exc_val, exc_tb) -> bool: if exc_type is None: print(f"[COMMIT] Session {self.session_id}, data saved") else: print(f"[ROLLBACK] {exc_type.__name__}: {exc_val}") return False # propagate the exception outward def execute(self, query: str) -> None: print(f" [SQL] {query}") # Success: automatic COMMIT with DBTransaction("SES_001") as tx: tx.execute("UPDATE accounts SET balance = balance - 350000 WHERE id = 'A'") tx.execute("UPDATE accounts SET balance = balance + 350000 WHERE id = 'B'") # Error: automatic ROLLBACK try: with DBTransaction("SES_002") as tx: tx.execute("UPDATE accounts SET balance = balance - 999999 WHERE id = 'A'") raise ValueError("CHECK constraint: balance < 0") except ValueError as e: print(f"[API] {e}")

Context managers

@contextmanager: a manager via a generator

You do not always need a full class. For simple cases there is the @contextmanager decorator from contextlib: code before yield is __enter__, code after yield is __exit__.

from contextlib import contextmanager import time @contextmanager def measure_time(operation: str): """Measures execution time""" start = time.perf_counter() print(f"[TIMER] Start: {operation}") try: yield # the code inside with runs here finally: ms = (time.perf_counter() - start) * 1000 print(f"[TIMER] {operation}: {ms:.1f}ms") @contextmanager def redis_lock(resource_id: str): """Simulated distributed lock""" key = f"lock:{resource_id}" print(f"[REDIS] acquiring {key}") try: yield key finally: print(f"[REDIS] releasing {key}") with measure_time("payment"): with redis_lock("account:UZ_5521") as lock: print(f" Working (lock={lock})") time.sleep(0.03)

Exit order is the reverse of entry order. The inner lock is released first.

logging module

What is logging

Logging: recording events while a program runs. What happened, when, on which server, in which function.

Analogy: an aircraft black box. After any incident an engineer opens the recording and sees what happened in the system before the failure.

  • There is no debugger in production. Only what is in the logs exists.
  • In microservices a transaction goes through several services: without logs you cannot find where it got stuck.
  • Audit. A bank must keep a record of who did what.

logging module

Configuring the logger

Three steps: get a logger by name, set its level, attach a handler with a format.

import logging import sys logger = logging.getLogger("PaymentService") logger.setLevel(logging.DEBUG) handler = logging.StreamHandler(sys.stdout) handler.setFormatter(logging.Formatter( '%(asctime)s [%(levelname)s] %(message)s' )) logger.addHandler(handler)

In production an additional RotatingFileHandler is added: it writes to a file and rotates by size so the log does not eat up disk space.

logging module

Usage: five levels

logger.debug("tx=TX_001 processing started") logger.info("TX processed. Amount: 500_000 UZS") logger.warning("Slow request: 120ms") logger.error("TX rejected: limit exceeded") logger.critical("DB unavailable, retry queue is full")
10:30:00 [DEBUG] tx=TX_001 processing started 10:30:00 [INFO] TX processed. Amount: 500_000 UZS 10:30:00 [WARNING] Slow request: 120ms 10:30:00 [ERROR] TX rejected: limit exceeded 10:30:00 [CRITICAL] DB unavailable, retry queue is full

The level is chosen by the event. In production usually INFO and above are filtered: DEBUG is too noisy.

logging module

exc_info=True: adds a traceback to the log

Without exc_info=True the log shows only the error message. With exc_info=True it adds the full traceback. This is crucial for debugging.

# Without exc_info logger.error(f"TX failed: {e}") # In the log: # "TX failed: Limit exceeded" # No file, no line, no call stack. # With exc_info=True logger.error(f"TX failed: {e}", exc_info=True) # In the log: # ERROR - TX failed: Limit exceeded # Traceback (most recent call last): # File "payment.py", line 30, in process # raise ValueError(...) # ValueError: Limit exceeded: 100000000

logging module

Broad except + mandatory logging

Sometimes you cannot predict all errors, and then except Exception is used. But that is not an excuse for silence: if you catch everything, you must log everything.

import logging logger = logging.getLogger(__name__) # standard: one logger per module def safe_check_fraud(tx: dict) -> dict: try: is_fraud = check_fraud(tx) return {"status": "BLOCKED" if is_fraud else "APPROVED"} except Exception as e: logger.error( f"Unexpected error in antifraud: {type(e).__name__}: {e}", exc_info=True ) return {"status": "ERROR", "reason": "Fraud check failed"}
Part of the messageWhat it gives
"Unexpected error in antifraud"Context: exactly where it failed
{type(e).__name__}Error class name, for filtering in Sentry
{e}Error text, to understand what happened
exc_info=TrueFull traceback, to find where it is in the code

This is called graceful degradation: the service does not crash, but the error is recorded.

logging module

Three levels of catching

# Ideal: specific exceptions, each with its own reaction try: response = external_api.call() except TimeoutError: retry_later() except ValueError: return {"status": "INVALID_INPUT"} # Acceptable: broad catch with mandatory logging try: is_fraud = check_fraud(tx) except Exception as e: logger.error( f"Unexpected error: {type(e).__name__}: {e}", exc_info=True ) return {"status": "ERROR"} # Forbidden: broad catch without logging try: is_fraud = check_fraud(tx) except Exception: pass # the error vanished, nobody knows

Without logs the error is silently swallowed. The service "keeps running", the business logic returns wrong answers, data gets corrupted. This is not protection, this is hiding the evidence.

Final task

SWIFT processor

Given: a list of payments. Some have corrupted fields, some violate business rules, some recipients are sanctioned. Task: the processor must not crash on any input and must count errors across three categories.

RAW_LEDGER = [ {"id": "SW_001", "from": "UZ_A", "to": "UZ_B", "amount": "350000"}, # OK {"id": "SW_002", "from": "UZ_C", "to": "UZ_C", "amount": "90000"}, # to self {"id": "SW_003", "from": "UZ_D", "amount": "120000"}, # 'to' missing {"id": "SW_004", "from": "UZ_E", "to": "UZ_F", "amount": "BROKEN"}, # not a number None, # not a dict {"id": "SW_005", "from": "UZ_G", "to": "UZ_H", "amount": "75000000"}, # limit exceeded {"id": "SW_006", "from": "UZ_I", "to": "SANCTION", "amount": "10000"}, # sanctions ]

Final task

Solution: validator

Three error classes by category. One validator: either OK or raise of the right type.

import logging logger = logging.getLogger("swift") MAX = 10_000_000 SANCTIONED = {"SANCTION"} class StructureError(Exception): pass # corrupted data class BusinessError(Exception): pass # business rules class ComplianceError(Exception): pass # sanctions def process_payment(p): if not isinstance(p, dict): raise StructureError(f"Not a dict: {type(p).__name__}") for field in ("from", "to", "amount"): if field not in p: raise StructureError(f"Missing field: {field}") try: amount = float(p["amount"]) except ValueError: raise StructureError(f"Amount is not a number: {p['amount']}") if p["from"] == p["to"]: raise BusinessError(f"Same account: {p['from']}") if amount > MAX: raise BusinessError(f"Limit: {amount}") if p["to"] in SANCTIONED: raise ComplianceError(f"Sanctions: {p['to']}")

Final task

Solution: batch processing

A single try/except with three branches. Each error type goes to its own counter and its own log level. The program does not crash under any circumstances.

def process_batch(payments): report = {"ok": 0, "structure": 0, "business": 0, "compliance": 0} for p in payments: try: process_payment(p) report["ok"] += 1 except StructureError as e: report["structure"] += 1 logger.warning(f"[STRUCT] {e}") except BusinessError as e: report["business"] += 1 logger.warning(f"[BIZ] {e}") except ComplianceError as e: report["compliance"] += 1 logger.error(f"[COMP] {e}") return report print(process_batch(RAW_LEDGER))
{'ok': 1, 'structure': 3, 'business': 2, 'compliance': 1}
